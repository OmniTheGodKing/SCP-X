# SCP-X: XCOM Improvement Roadmap

Companion to `audit.md`. It refines and orders the 4J plan already in `docs/ROADMAP.md`. It
keeps that roadmap's decisions:
- vision is all round, as in XCOM 2;
- hearing stays as built;
- 4H (combat variety and progression) comes after the combat foundation;
- 4D (story and endgame) is last;
- Phase 5 (3D) is later still.

Section numbers such as "audit 2.5" refer to the audit.

**Principles:**
- **Foundations first.** No dependent feature before the system it stands on.
- **Every phase ships on its own.** Existing missions, anomalies and saves keep working, and each phase ends with its
  tests passing.
- **Keep the public helpers.** `canSee`, `sightFrom`, `rawSight`, `lineOfFire`, `fireLine`, `bfs` and the rest keep
  their names and become wrappers, so the anomaly code and the 58 sight call sites don't have to change at once.
- **No GPL or unlicensed code is copied.** References are used for ideas only.
- **No new complexity without a visible gameplay gain** stated in its task.

Each task lists:
- Objective
- Systems affected
- Files
- Approach
- Dependencies
- Acceptance criteria
- Tests
- Risks
- Gameplay gain

## Phase 0: Safety net (no gameplay change)

These come first because every later phase needs them to be testable and safe for players.

### 0.1 Bring the tests into the repository and make them portable
- **Objective:** one `npm test` that runs every suite from any checkout.
- **Systems affected:** testing only.
- **Files:** `tests/*.e2e.cjs`, `package.json`, a new `tests/run.cjs`. Scripts from the session scratch folder that
  still matter (economy simulations, the earlier acceptance checks, the audit's consistency probe) get copied in.
- **Approach:**
  - Resolve `dist/index.html` relative to the repository.
  - Write screenshots to `tests/out/` (git-ignored).
  - Have a runner that prints a summary and exits non-zero on failure.
- **Dependencies:** none.
- **Acceptance criteria:** `npm run build && npm test` passes on a clean clone. No absolute paths remain in `tests/`.
- **Tests:** the suite itself.
- **Risks:** the browser tests need Playwright, which isn't a project dependency. Adding it is a dependency change,
  so it needs approval first.
- **Gameplay gain:** none directly. It stops regressions.

### 0.2 Seeded randomness
- **Objective:** every random roll in a mission and in the campaign comes from a seeded generator, so any situation can
  be reproduced.
- **Systems affected:** all 175 `Math.random` call sites.
- **Files:** a new `src/core/rng.ts`; `src/game/*`, `src/campaign/*` (mechanical replacement); `types.ts` (a seed on
  `MissionSetup` and `Campaign`).
- **Approach:**
  - A small PRNG (for example mulberry32 or splitmix), with its state saved in the mission and campaign.
  - Separate streams for combat, AI, the map and cosmetics, so animation randomness doesn't shift combat rolls.
- **Dependencies:** none.
- **Acceptance criteria:**
  - Same seed and same inputs give the same mission log.
  - The old saves load, with a seed assigned on load.
- **Tests:** a determinism test (run a scripted mission twice and compare logs); the save migration test (0.4).
- **Risks:** a missed call site breaks determinism. Fix: a lint check that fails on `Math.random` outside `rng.ts`.
- **Gameplay gain:** indirect. It enables 1.x and 7.x testing and makes bug reports reproducible.

### 0.3 Mid-mission save, and no silent loss on page close
- **Objective:** closing or reloading the page mid-mission resumes the mission instead of counting it lost.
- **Systems affected:** the mission lifecycle (audit 2.15), saves (audit 3.14).
- **Files:** `src/game/state.ts`, `mission.ts`, `src/core/grid.ts` (serialize `Level` state: grid, doors, glass,
  version), `src/campaign/save.ts`, `src/main.ts`, `campaign.ts` (`resolveInterrupted` becomes "resume").
- **Approach:**
  - Serialize `S` and the mutable parts of `L` at the start of each player turn (the `Set`s and `Map`s become arrays).
  - Restore on load.
  - Keep `resolveInterrupted` only for unreadable mission saves.
  - An Ironman campaign keeps one autosave, no reloads.
- **Dependencies:** 0.2, so a resumed mission continues the same random sequence.
- **Acceptance criteria:**
  - Reload during turn 3 of each mission kind and get the same units, map, fog of war and turn.
  - No exposure penalty.
- **Tests:** a save, restore and compare round trip for every mission kind.
- **Risks:** state that lives only in closures or UI. Fix: a test that compares full state after the round trip.
- **Gameplay gain:** high for a browser and phone game: no lost missions from a closed tab.

### 0.4 Save migration tests
- **Objective:** prove every save version upgrades to the current one.
- **Systems affected:** saves.
- **Files:** `src/campaign/save.ts`; `tests/fixtures/save-v*.json` (generated by playing to a point under each old
  version, or hand-built to the documented shapes).
- **Approach:**
  - A fixture per version from 2 to 24, upgraded and then validated (required fields present, `version === 24`).
  - On failure, keep a backup copy instead of discarding the save.
- **Dependencies:** 0.1.
- **Acceptance criteria:**
  - All fixtures upgrade.
  - A corrupted save is kept as a backup and reported, not dropped.
- **Tests:** the fixtures.
- **Risks:** old fixtures can't be produced exactly. Fix: build them from the migration steps' own assumptions.
- **Gameplay gain:** players don't lose campaigns.

### 0.5 Attribution
- **Objective:** credit every SCP used, in the README and in-game, as CC BY-SA 3.0 and the README's own rule require.
- **Systems affected:** documentation and UI.
- **Files:** `README.md`, `src/game/notes.ts` or a credits panel in `hubView.ts`.
- **Approach:**
  - A credits table: SCP, article URL, author.
  - Author names must be checked on scpwiki.com. This session's network can't reach it, so either the owner supplies
    them or the host is allowed.
- **Dependencies:** none.
- **Acceptance criteria:** every SCP in `SCP_DEFS` has a credit line in both places.
- **Tests:** a static test that every SCP ID has a credit entry.
- **Risks:** wrong author names. Fix: verify each one on the wiki.
- **Gameplay gain:** none. It is license compliance.

### 0.6 Remove "default to SCP-173" fallbacks
- **Objective:** an unknown or missing anomaly ID is an error, not SCP-173.
- **Systems affected:** mission setup.
- **Files:** `src/game/mission.ts` (`setup.scp ?? "173"`), `turn.ts`, `missionView.ts`.
- **Approach:** require `setup.scp` on containment missions; assert at setup.
- **Dependencies:** none.
- **Acceptance criteria:** every mission kind starts with its correct anomaly or none. No `?? "173"` remains.
- **Tests:** start each mission kind with each SCP.
- **Risks:** an old save with an empty `scpId`. Fix: a migration in 0.4.
- **Gameplay gain:** stops the class of bug that broke object thefts.

## Phase 1: Tactical lab and golden scenarios (4J step J0)

### 1.1 The lab screen
- **Objective:** a place to build a situation and watch every rule.
- **Systems affected:** UI, debug.
- **Files:** a new `src/ui/lab.ts`; `debug.ts` (entry point); `render.ts` (overlays); `main.ts`.
- **Approach:**
  - A blank grid or any map.
  - Painting: walls, half and full cover, windows (ordinary or reinforced, broken or not), door states, partitions,
    smoke, and light (once Phase 4 exists).
  - Units: place, drag and delete team members, Insurgents and civilians.
  - Overlays for the selected viewer:
    - visible tiles (later: detected and identified);
    - the eye points and the trace to the hovered tile, with each obstacle crossed;
    - cover shields per direction for the hovered unit;
    - the full hit-chance breakdown for the hovered enemy;
    - flank markers;
    - overwatch lanes.
  - Scenarios save and load as JSON.
- **Dependencies:** 0.2 (seeded, so the lab is reproducible).
- **Acceptance criteria:** every audit scenario can be built and inspected without code changes.
- **Tests:** a smoke test that the lab loads each saved scenario.
- **Risks:** scope creep into a map editor. Keep it to these tools.
- **Gameplay gain:** none directly. It makes every later phase verifiable by the owner, not just by scripts.

### 1.2 Golden scenarios recording today's behaviour
- **Objective:** a named set of scenarios with expected answers, run against the current rules to record where they
  are wrong. The failures become the targets for Phases 2 to 4.
- **Systems affected:** testing.
- **Files:** `tests/scenarios/*.json`, `tests/geometry.e2e.cjs`.
- **Approach:** scenarios:
  - a long hallway (40 tiles);
  - an open room;
  - a diagonal across a room;
  - an outside corner and an inside corner;
  - a doorway seen straight on and at 30°, 45° and 60°;
  - a window wall (ordinary and reinforced);
  - a partition;
  - one crate;
  - a row of three crates, from the middle and from the end (the owner's drawings);
  - half cover;
  - a long-range engagement;
  - smoke.

  Each records, for set positions: can see, can shoot, cover, flanked, hit chance.
- **Dependencies:** 1.1, for building and viewing them.
- **Acceptance criteria:** the scenarios run; current failures are listed in the test output as "expected failure"
  until fixed.
- **Tests:** the suite.
- **Risks:** none.
- **Gameplay gain:** none directly.

### 1.3 The consistency probe as a permanent test
- **Objective:** keep the audit's measurements (sight symmetry, see-but-can't-shoot) as a regression with a target of
  zero unexplained contradictions.
- **Files:** `tests/consistency.e2e.cjs` (from the audit probe).
- **Dependencies:** 0.1.
- **Acceptance criteria:**
  - Contradiction counts are reported per map.
  - After Phase 2, they reach 0, except reinforced glass and documented rules.
- **Gameplay gain:** none directly.

## Phase 2: One geometry kernel (4J step J1)

### 2.1 Obstacle model
- **Objective:** every map tile becomes zero or more obstacles, each with:
  - a shape: full tile, or a thin segment on the tile's centre line, horizontal or vertical;
  - a height: low (waist), high (head and up), structural (wall);
  - flags: blocks sight, blocks fire;
  - hit points: where destructible.
- **Systems affected:** the map (audit 2.1).
- **Files:** a new `src/core/obstacles.ts`; `grid.ts` (build obstacles on load and on every `bump()`); `sight.ts`
  (thin-wall inference moves here as a conversion step).
- **Approach:**
  - Derive from the existing characters: `#` is structural (thin when in a one-tile line between open ground on both
    sides, as now), `H` is high, `h` is low, `w`/`W` are thin and transparent with a low sill, `p` is a thin
    structural partition, doors are thin or full by state.
  - No map file changes.
- **Dependencies:** 0.1.
- **Acceptance criteria:**
  - Every map converts.
  - Walkability is identical to today (checked tile by tile).
  - Obstacle kinds match a hand-checked sample per map.
- **Tests:** conversion golden files per map; the walkability round trip.
- **Risks:** thin-wall edge cases at junctions. Fix: the lab view and golden files.
- **Gameplay gain:** predictable geometry the player can read from the art.

### 2.2 One trace
- **Objective:** `trace(a, b)` walks a segment in continuous coordinates and returns every obstacle crossed, with its
  height and position along the segment.
- **Files:** `src/core/trace.ts` (it generalises the existing `walk()` DDA in `sight.ts:38`).
- **Approach:** the same corner rule as today (a ray can't squeeze between two blocks touching at a corner). Results
  are cached per map version.
- **Dependencies:** 2.1.
- **Acceptance criteria:** the trace agrees with today's `walk()` on every ray where today's rules are intended (golden
  scenarios), and fixes the cases 1.2 flagged.
- **Tests:** unit tests on synthetic grids. These are headless: `src/core` has no UI dependencies today, so they can run
  in Node directly.
- **Risks:** performance. The traces are cheap; keep the per-version cache.
- **Gameplay gain:** none alone. It is the base for 2.3 to 2.5.

### 2.3 Eye points and peeking from geometry
- **Objective:** a unit looks from its tile centre, plus a step-out point at each end of any adjacent high obstacle
  that ends in open ground, as XCOM does. No rule filters.
- **Files:** `sight.ts` (`viewSpots` is replaced).
- **Approach:**
  - For each orthogonally adjacent high obstacle, find where it ends along its line within one tile. A step-out point
    exists there if that tile is open.
  - Low obstacles never block the shooter's own view.
- **Dependencies:** 2.1, 2.2.
- **Acceptance criteria:** the owner's three-crate and single-crate drawings hold without tuning constants
  (`LEAN_SIGHT` removed).
- **Tests:** golden scenarios.
- **Risks:** it changes how far leaning reaches in some layouts. Fix: the lab and playtest.
- **Gameplay gain:** peeking the player can predict from the map.

### 2.4 Visibility as exposure
- **Objective:** a target is visible if enough of its body (sample points on a figure inside its tile) is reachable
  from the best eye point. The fraction becomes "exposure" for the hit chance.
- **Files:** `sight.ts` (`visFrac` and `bestView` are replaced).
- **Approach:** symmetric pairs by construction: the same eye-point rule applies to both units, and exposure is
  computed both ways and the rule documented. OpenXcom's voxel exposure is the idea, in 2D.
- **Dependencies:** 2.3.
- **Acceptance criteria:** the consistency test (1.3) shows 0 unexplained asymmetries.
- **Tests:** golden scenarios; the consistency test.
- **Risks:** changes balance (more or less sight in places). Fix: playtest after the phase.
- **Gameplay gain:** "if I can see them, they can see me", and it holds.

### 2.5 Line of fire on the same trace, and every caller moved over
- **Objective:**
  - `lineOfFire` uses the same eye point and the same trace as sight, and differs only by the "blocks fire" flag
    (reinforced glass).
  - `canSee`, `sightFrom`, `rawSight` (SCP-173: no step-out), noise wall counts and the AI all call the kernel.
- **Files:** `combat.ts`, `state.ts`, `insurgency.ts`, `noise.ts`, `scp173.ts`, `scp4b.ts`.
- **Dependencies:** 2.4.
- **Acceptance criteria:** see-but-can't-shoot is 0 except through reinforced glass. All existing suites still pass.
- **Tests:** the consistency test; all acceptance suites.
- **Risks:** SCP rules depend on subtle sight behaviour. Fix: `accept4b`, `window` and `accept4i` must pass unchanged.
- **Gameplay gain:** the core trust problem is fixed: what you see is what you can shoot.

## Phase 3: Cover from the line of fire (4J step J2)

### 3.1 Geometric cover and flanking
- **Objective:** a target's cover against a shooter is the tallest obstacle the trace crosses in the band of the
  target's own tile or edge facing the shooter. High is full, low is half, none is flanked.
- **Files:** `combat.ts` (`coverAgainst` and `coverTileFacing` are replaced), `abilities.ts` (`hasCover`),
  `insurgency.ts`.
- **Dependencies:** 2.5.
- **Acceptance criteria:**
  - In the cover matrix (every obstacle kind × 16 shooter bearings), cover matches the XCOM convention.
  - Windows, partitions and doors count by height.
- **Tests:** the cover matrix; golden scenarios.
- **Risks:** a balance shift (more cover from windows). Fix: playtest.
- **Gameplay gain:** flanking that works the way the player reads the map.

### 3.2 The move cursor preview
- **Objective:** hovering a destination shows:
  - the cover shields it would have against each known enemy;
  - flank warnings;
  - the enemies that would be visible from it;
  - overwatch it would cross.
- **Files:** `render.ts`, `missionView.ts`.
- **Dependencies:** 3.1 (and 6.1 for overwatch lanes).
- **Acceptance criteria:** the shields shown equal `coverAgainst` for the dice.
- **Tests:** lab UI checks.
- **Risks:** clutter. Show only for hovered tiles.
- **Gameplay gain:** high. This is XCOM's main readability tool.

## Phase 4: Perception and light (4J step J3)

### 4.1 Light map
- **Objective:** a per-tile light level from:
  - map lights (Site-19's lights while the power is on, street lamps, lit rooms);
  - flares, fire, muzzle flashes;
  - day and night, and weather.
- **Files:** a new `src/core/light.ts`; `maps.ts` (light sources per map, as data); `fire.ts`; `combat.ts` (muzzle
  flash); `state.ts` (`lit` is replaced).
- **Dependencies:** 2.1.
- **Acceptance criteria:**
  - A lit corridor at night is visible end to end.
  - An unlit field at night is not.
  - Power loss on emergency missions darkens the site.
- **Tests:** golden night scenarios.
- **Risks:** map authoring work, to place lights.
- **Gameplay gain:** night missions about light and darkness, not a flat 9 tiles.

### 4.2 Detection and identification
- **Objective:** after geometry, each viewer–target pair has a state: unseen, detected (a silhouette, position only)
  or identified (side, weapon, type).
- **Files:** a new `src/game/perception.ts`; `state.ts` (`S.vis` becomes a per-tile state); `render.ts` (contact
  markers); `missionView.ts` (unknown contact panel); `insurgency.ts` (the AI uses it); `noise.ts` (hearing feeds
  "detected").
- **Approach:** a score from:
  - distance;
  - light at the target;
  - target movement this turn;
  - concealment (in cover, still);
  - smoke density along the trace;
  - observer traits and gear;
  - weather.

  Thresholds give the three states. Concealment's 4-tile rule becomes the unalerted-observer threshold.
- **Dependencies:** 2.5, 4.1.
- **Acceptance criteria:**
  - A long-hallway ladder: identified, then detected, then unseen as distance and light change.
  - The concealment tests still pass with the numbers mapped over.
- **Tests:** perception tables; the concealment scenarios.
- **Risks:**
  - Overcomplicated rules. Keep to a few inputs, each shown in a tooltip.
  - A balance shift.
- **Gameplay gain:** distance and darkness matter without blocking geometry. Scouting matters.

### 4.3 Firing at unidentified contacts (owner decision needed)
- **Objective:** allow shooting at a detected but unidentified contact, at a penalty, with the risk it's a civilian or
  a D-Class.
- **Files:** `combat.ts`, `turn.ts`.
- **Dependencies:** 4.2.
- **Acceptance criteria:** as decided by the owner.
- **Tests:** shooting a silhouette that is a civilian applies the exposure penalty.
- **Risks:** player frustration. Make it opt-in per shot, with the risk shown.
- **Gameplay gain:** a real SCP-flavoured dilemma.

### 4.4 Smoke density
- **Objective:** smoke attenuates sight per tile crossed instead of being a wall, as OpenXcom does.
- **Files:** `sight.ts`, `turn.ts` (grenades).
- **Dependencies:** 4.2.
- **Acceptance criteria:** fresh smoke hides at 2 or more tiles' depth; thin smoke only reduces detection.
- **Tests:** a smoke ladder.
- **Gameplay gain:** smoke becomes a positioning tool, not an on/off switch.

## Phase 5: Accuracy, damage and status (4J step J4)

### 5.1 Range curves per weapon
- **Objective:** smooth accuracy by distance for each weapon type (and per model where it differs), as data.
- **Files:** `data/weapons.ts` (`rangeMod` becomes curve tables).
- **Dependencies:** none (it can go earlier), but tune after Phase 2.
- **Acceptance criteria:** the hover breakdown shows the range term. Tables are documented in-game.
- **Tests:** a hit-chance table by distance per weapon.
- **Gameplay gain:** weapon choice by role and distance.

### 5.2 Exposure instead of "partly hidden"
- **Objective:** the −15 "partly hidden" from ray sampling is replaced by an exposure term from 2.4, and leaning is
  no longer penalised beyond what exposure says.
- **Files:** `combat.ts` `shotInfo`.
- **Dependencies:** 2.4.
- **Acceptance criteria:** golden scenarios show the expected modifiers.
- **Tests:** the hit-chance table.
- **Gameplay gain:** modifiers the player can explain.

### 5.3 Traced misses (stray rounds)
- **Objective:** a miss continues along its trace, with scatter, and can strike cover (damage, see 7.1), glass, or
  another unit (a low chance).
- **Files:** `combat.ts` `fire`.
- **Dependencies:** 2.2.
- **Acceptance criteria:** stray-round statistics within tolerance in seeded runs.
- **Tests:** a seeded Monte Carlo check.
- **Risks:** friendly-fire frustration. Keep the chance low and show it.
- **Gameplay gain:** firing lines matter; civilians in the line are a risk.

### 5.4 Graze band and optional damage falloff
- **Objective:** XCOM 2-style grazes near the hit threshold (partial damage); falloff for shotguns and SMGs past their
  range.
- **Files:** `combat.ts`, `data/weapons.ts`.
- **Dependencies:** 5.1.
- **Acceptance criteria:** documented numbers; the breakdown shows them.
- **Tests:** a damage table.
- **Gameplay gain:** fewer all-or-nothing swings.

### 5.5 Status registry
- **Objective:** one system for timed statuses (apply, tick, expire, show): bleeding, burning, blinded, panicked,
  stunned, suppressed, marked, staggered and the rest.
- **Files:** a new `src/game/status.ts`; `types.ts` (the `xxxUntil` fields move into a list); callers in `combat.ts`,
  `turn.ts`, `abilities.ts`, the SCP files.
- **Dependencies:** 0.2.
- **Acceptance criteria:** the same durations and effects as today (no number changes); statuses listed on the unit
  panel.
- **Tests:** apply, tick and expire for each status; all suites pass.
- **Gameplay gain:** readability, and a base for 6.2.

## Phase 6: Actions, reactions and suppression (4J step J5)

### 6.1 Action table
- **Objective:** every unit action (move, dash, shoot, reload, overwatch, hunker, abilities, items) declared once:
  cost, ends turn, targets, validity, and its AI value hook.
- **Files:** `abilities.ts` (extended); `turn.ts` (handlers read the table instead of writing `ap` directly).
- **Dependencies:** none.
- **Acceptance criteria:** no `ap =` or `ap -=` outside the action executor. All suites pass.
- **Tests:** a cost table test per action.
- **Gameplay gain:** consistency, and the AI gets the same options as the player.

### 6.2 One reaction system
- **Objective:** any unit with a reaction stance (overwatch for now) fires at the first hostile movement it perceives,
  of any side: Insurgents, SCP-049-2, SCP-939 instances, rioters.
- **Files:** `combat.ts` `moveUnit` (the reaction loop is replaced); `insurgency.ts` (enemy overwatch for all roles).
- **Dependencies:** 4.2, 6.1.
- **Acceptance criteria:**
  - Overwatch triggers on each hostile type.
  - Not on undetected movement.
  - Rapid reaction, Covering fire and tracers work as now.
- **Tests:** a reaction matrix in the lab.
- **Gameplay gain:** overwatch becomes a tool on every mission, and a threat from the enemy.

### 6.3 XCOM 2 suppression
- **Objective:**
  - A suppressed unit loses aim and its overwatch.
  - If it moves, it draws a reaction shot from the suppressor.
  - It lasts until the suppressor moves, is hit hard or the turn passes.
  - Suppressing uses 2 rounds.
- **Files:** `abilities.ts`, `combat.ts`, `status.ts`.
- **Dependencies:** 5.5, 6.2.
- **Acceptance criteria:** as stated; the AI can use it (7.3).
- **Tests:** suppression scenarios.
- **Gameplay gain:** locking an enemy down becomes a real choice.

## Phase 7: Destruction, and the AI on the shared model (4J steps J6 and J7)

### 7.1 Destructible cover
- **Objective:** obstacles have hit points. Explosions and stray rounds wear them down: full cover to half to rubble.
  Pillars become destructible by heavy explosives.
- **Files:** `obstacles.ts`, `grid.ts` (`blastStructure`), `combat.ts`, `turn.ts`.
- **Dependencies:** 2.1, 5.3.
- **Acceptance criteria:** a crate takes N hits to drop a level; a grenade drops full to half; caches update.
- **Tests:** destruction scenarios.
- **Gameplay gain:** explosives clear cover, as in XCOM.

### 7.2 Separate rules from presentation
- **Objective:** combat and AI run without the UI: rules return events (shot, hit, moved, status), and the UI plays
  them with the timing it wants.
- **Files:** `combat.ts`, `turn.ts`, `insurgency.ts`, the SCP AI files, `state.ts` (`fx`, `log` and `sleep` move to
  an event queue).
- **Approach:**
  - Start with `fire` and `moveUnit`.
  - The UI subscribes to events and animates them.
  - `sleep` disappears from rules code.
- **Dependencies:** 0.2.
- **Acceptance criteria:**
  - A mission's enemy phase can run headless in Node.
  - The visible game is unchanged (the `accept4g` presentation tests pass).
- **Tests:** headless combat tests; `accept4g`.
- **Risks:** large and touches many files. Do it file by file behind wrappers.
- **Gameplay gain:** faster enemy turns, a "skip enemy animations" option, and the AI can evaluate moves by
  simulation.

### 7.3 Utility AI
- **Objective:** each enemy picks the best of all its options, scored on the shared kernel.
- **Files:** `insurgency.ts` (reorganised into `ai/positions.ts`, `ai/actions.ts`, `ai/roles.ts`); `ciTactics.ts`;
  `rivals.ts`.
- **Approach:**
  - **Candidate positions:** within its real move and dash range (`moveOf`). Each is scored for:
    - cover against each detected threat (3.1);
    - exposure (expected incoming hits from threats that could see the spot, and overwatch lanes);
    - flank opportunities;
    - distance to its objective;
    - role weights (sniper keeps range, flanker seeks flanks, officer stays back).
  - **Actions:** shoot, overwatch, grenade (clustered targets or cover to destroy), suppress, reload, hunker, fall
    back, scored by expected value.
  - **Squad level:** one pod coordinator assigns roles each turn (one suppresses, one flanks), as OpenApoc separates
    its tactical AI from its unit AI.
  - **Tuning:** weights live in data and can be shown in the lab.
- **Dependencies:** 2.5, 3.1, 4.2, 6.1, 6.2, 6.3, 7.2, 0.2.
- **Acceptance criteria:** seeded lab scenarios:
  - it takes cover against the threat;
  - it flanks an exposed operative when it can;
  - it avoids overwatch lanes;
  - it grenades three clustered targets;
  - it suppresses before advancing when outnumbered.
- **Tests:** the AI scenario suite.
- **Risks:**
  - An AI that is too good. Fix: difficulty scales its weights and how far it looks ahead.
  - Turn time. Fix: the score caches from Phase 2.
- **Gameplay gain:** enemies that use cover, flanks and overwatch like the player must.

### 7.4 Pathing without global flags
- **Objective:** `bfs` takes an options object (vaulting, link access, slow tiles) instead of module-level flags.
- **Files:** `grid.ts`, `turn.ts`, every `bfs` caller.
- **Dependencies:** none (it can go any time before 7.3).
- **Acceptance criteria:** no `setVault`, `setLinkAccess` or `setSlow` remain. Pathing results are unchanged.
- **Tests:** reach sets per unit type.
- **Gameplay gain:** none directly. It removes a latent bug source.

## Phase 8: Data-driven anomalies and missions (before 4H and 4D)

### 8.1 Anomalies as definitions
- **Objective:**
  - Replace the single `S.statue` slot and the `has173`, `has049`, `has106` flags with a list of anomaly units, each
    with a definition: behaviour module, capture rule, sight rules, capture kit, text.
  - This enables a cascade breach (two anomalies at once).
